# Agent skills (repo `agent-skills`)

Skills that teach any coding agent to read and write Synod. Claude Code
is the primary target; the same content is exposed for other agents.

## Layout

`agent-skills` is a Claude Code plugin whose parts are partly written by hand
and partly generated from pinned releases (decision 97).

```
.claude-plugin/plugin.json       name synod, version, description, author, homepage, repository, license
.claude-plugin/marketplace.json  marketplace synodlang with the plugin synod (source "./")
skills/synod/SKILL.md            hand-written entry point (Claude Code skill format)
skills/synod/reference/
    grammar.md                   hand-written, condensed from spec/02
    phrases.md                   hand-written, condensed from spec/03
    contexts.md                  hand-written, condensed from spec/05
    canonical.md                 GENERATED: spec/10 verbatim
    trace-events.md              GENERATED: spec/08 verbatim
    std-catalog.md               GENERATED by `synod doc --catalog`
    errors.md                    GENERATED by `synod explain --catalog`
    examples/                    GENERATED: the examples repo at the pinned commit
AGENTS.md                        GENERATED: SKILL.md without front matter
versions.env                     the pins
tools/sync/                      Go, standard library only: regenerates, `--check` fails on any difference
.github/workflows/ci.yml         text check, sync and stale jobs
.github/workflows/release.yml    on `v*` tags: the tarball and SHA256SUMS
```

**Pins.** `versions.env` holds `DSL_VERSION`, `SYNOD_VERSION`,
`SYNOD_LINUX_AMD64_SHA256`, `EXAMPLES_VERSION` and `EXAMPLES_COMMIT`.

**Generated files.**

| File | Generated from |
| --- | --- |
| `canonical.md`, `trace-events.md` | `spec/10` and `spec/08` of `dsl` at `DSL_VERSION`, with relative links made absolute at that tag |
| `std-catalog.md` | `synod doc --catalog` of the pinned `synod` |
| `errors.md` | `synod explain --catalog` of the pinned `synod` |
| `examples/` | the examples repo at `EXAMPLES_COMMIT` (`synod.mod`, `*/*.synod`, `README.md`) |
| `AGENTS.md` | `SKILL.md` without front matter, with `reference/` paths rewritten to `skills/synod/reference/` |

The generated Markdown files start with the line `Generated by …. Do not
edit.` The hand-written reference files each start with `<!-- condensed from
dsl <tag> spec/0N -->`; `tools/sync --check` fails when that tag is not
`DSL_VERSION`, so every `dsl` release forces a review of them. `plugin.json`'s
`version` must equal the newest version of the CHANGELOG.

## SKILL.md (outline)

```markdown
---
name: synod
description: Read, write, check and run Synod (.synod) programs that model
  distributed systems, system designs and database internals for animation.
  Use whenever a task mentions Synod, .synod files, synod.mod, or asks to
  "animate" or "simulate" a protocol in a Synod workspace.
---

# Writing Synod

1. Look before writing: run `synod doc` to list the packages, search the
   workspace for an existing package, and to use the examples run
   `synod get github.com/synodlang/examples@v0.2.1`, then
   `use github.com/synodlang/examples/twopc`. Prefer writing only a main file
   (`define main`); never copy or rewrite an existing package, and never edit
   `vendor/`.
2. Every argument is one item: parenthesize every nested phrase and every
   multi-item condition. `if (n.Role is "leader")`, `set n.x to (n.x plus 1)`.
3. Qualify every imported name (`net.Send`, `gossip.Join`,
   `n.gossip.Known`); never qualify your own package's names (`n.Known`,
   `Quorum`).
4. Node code names its node with a receiver: `define [n: Node] Version`,
   `when [n: Node] (net.Received …)`, `define [n: Node] start`. It touches
   only `n`'s state and talks to other nodes with `net.Send m from n to p`.
   `deliver` and faults live in `define main`.
5. Types are explicit: `[ns: list of Node]`, `[m: map of node to number]`.
   A `node` has no fields; `Node` or `pkg.Node` does.
6. Looks are optional: `std/look/basic` animates everything by default.
7. Run `synod fmt`, then `synod check` until clean, then `synod run` and
   confirm the trace shows what was asked. Never hand back unchecked code.
8. Piped output is the one-line form with a hint, which is what you read.
   Use `synod check --json` for spans, edits and quick fixes, or
   `--style rich` to see the source line. `synod explain <code>` explains
   any diagnostic with an example and its fix.

Reference files: grammar.md, phrases.md, contexts.md, canonical.md,
std-catalog.md, trace-events.md, errors.md, examples/.
```

`SKILL.md` stays under about 200 lines, stamps the `dsl` version it was written
for, and carries the budget rules of `07-claude-integration.md`.

## Sync rules

- `tools/sync` regenerates every generated file from the pins;
  `go run ./tools/sync --check` exits 1 on any difference, on a hand-written
  reference file stamped with another `dsl` tag, and on a `plugin.json` version
  that is not the CHANGELOG's newest.
- CI has three jobs. **sync** downloads the pinned `synod` (checksum
  verified), checks out `dsl` and `examples` at the pins, runs `go run
  ./tools/sync --check`, then runs `synod fmt --check` and `synod check` on
  `reference/examples` and on every `synod` code block of the skill files that
  starts with `# package`, as a whole file in a temporary module. **stale**
  (on pushes, pull requests and daily) fails when `git ls-remote --tags` shows
  a higher `v0.2.x` tag of `dsl`, `compiler` or `examples` than the pin
  (`std` is covered through the compiler, which embeds it). **text** is the
  repository's text check. The sync workflow lives in `agent-skills`, not in
  the organization's `.github`.
- Every `dsl` release is followed by an `agent-skills` release with its own
  patch number (decision 61).
- Every example in the skill must pass `synod check`.
